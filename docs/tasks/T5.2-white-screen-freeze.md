# T5.2 — White screen and window freeze during long network play

**Milestone:** M5 (backlog, high priority: a failure visible to the player) · **Depends on:** T3.6, T4.5, T4.6 · **Size:** M

## Symptom (per the user, 2026-10-05)
During a long network game (Mac ↔ Windows laptop, an 8 GB laptop) the window periodically turns **completely white and stops responding**, as if the game had crashed. It can happen right in the middle of a game. After that only restarting the game helps. On the Windows laptop it happened noticeably more often; on macOS it also happened, but less often. Not established: which side (host or client) went white more often, whether it happens in solo play, after how long, on which levels.

"White, not responding" is a sign of a hung or crashed renderer process (or a lost GPU process). First **tell the cases apart** (hang / renderer crash / GPU crash / WebGL context loss), then fix the cause, not the symptom.

- `CLAUDE.md`, `docs/00-overview.md`, `docs/01-architecture.md`, `docs/03-frame-and-network-protocol.md`, `docs/05-verification.md` §9

- `tools/perf/measure.ts` (`--lose-context`, memory by process type), `electron/perfLog.ts`

## Steps
1. **In-app diagnostics (always on, cheap).** Writes to `<userData>/crash.log` (append, rotation ~1 MB, ISO time, role host/client/local, version, platform):
   - main: `webContents` `render-process-gone` (reason, exitCode), `unresponsive`/`responsive`, `did-fail-load`; `app` `child-process-gone` (type, reason — GPU!), `gpu-info-update`; `uncaughtException`/`unhandledRejection`;
   - renderer: `webglcontextlost`/`webglcontextrestored`, `window.onerror`, `unhandledrejection`, simulation worker errors;
   - once every 30 s a state line: RAM per process (`app.getAppMetrics`), queue sizes (the client's jitter buffer, the host ws `bufferedAmount`, the number of atlas pages, the number of live audio nodes), `netState`, tick number.
   The log must not slow the game down (asynchronous writes, no write per frame).
2. **Reproduction.** A "soak" script (`tools/perf/soak.ts`, modeled on `measure.ts`): two Electron instances host+client over `127.0.0.1`, then the same through `tools/net/latency-proxy.ts` (30 ± 15 ms), 30–60 minutes of scripted input with level restarts; once a minute it samples the memory of all processes and the queue sizes, and writes a table and the slope (MB/hour). Separately — solo with no network. The goal is to find memory or queue growth, or a crash. If it does not reproduce on the Mac — apply a pressure level: `--tier=2x`, a memory limit, background CPU/GPU load.
3. **Check the hypotheses** (one by one, recording the result; do not guess): (a) a leak/growth of the frame queue on the client when rendering is slower than the host (backpressure on the client side, not only the host); (b) atlas pages/textures/ImageBitmap are not released on level changes; (c) audio: AudioContext nodes for oneShots/loops are not disconnected; (d) growing arrays in the worker (Task/Tween, effects, ragdoll, particles), the passenger list, events; (e) the renderer on an 8 GB laptop runs out of memory (tier 2x by default) or the GPU process is lost on integrated graphics (including on minimizing/hiding the window, changing the screen, display sleep); (f) window hidden/occluded → `requestAnimationFrame` throttling, frames pile up and are then processed all at once (a long main-thread block); (g) heavy synchronous code in the main process (writing save/settings/perf-log) blocks IPC.
4. **Fix the cause found** (or causes) in the remaster code: bound the queues (drop old frames with a request for a key/full frame instead of accumulating), release resources, remove blocking code. Game logic and golden replays do not change.
5. **Safety net (in addition to the fix, not instead of it):** on `render-process-gone`, `unresponsive` > 10 s or `child-process-gone` (GPU): write to `crash.log`, recreate the window/reload the renderer into the menu (do not touch the save); for the client — show "Connection lost" and return to the menu, for the host — correctly close the client's slot so that the client can connect again. Show the player a clear message once, in the bitmap font (not a system dialog over fullscreen).
6. Tests: pure queue-bounding/backpressure logic; a unit test for `crash.log` formatting/rotation; e2e: forcibly crash the renderer (`webContents.forcefullyCrashRenderer()` in test mode) → the application recovered into the menu, a log entry exists; `--lose-context` still works.

## Outputs
`electron/crashLog.ts` (+ wiring in `electron/main.ts`), queue/resource fixes in `src/app`, `src/render`, `src/audio`, `src/net`, `tools/perf/soak.ts`, tests, a section in `docs/05` ("long play") and a "how to send crash.log" instruction in the user README. If several causes are found — a "hypothesis → checked → result" table in the report.

## Acceptance criteria
- [ ] `crash.log` is created in userData and records the step 1 events; on an artificial renderer and GPU crash (a `--disable-gpu-sandbox`-like check or killing the GPU process) there is an entry and the game returned to the menu.
- [ ] Soak on the Mac: 60 minutes host+client (and through the latency proxy): RAM growth of all processes after the first 10 minutes ≤ 5% per hour, the queues do not grow; the table is in the report. If a cause was found and fixed — attach "before/after".
- [ ] Each of the hypotheses (a)–(g) is closed: confirmed and fixed, or refuted by measurement.
- [ ] Golden replays and `npm run check` unchanged/green; the `docs/05` §9 budgets did not get worse.
- [ ] **Needed from the user:** a long network game Mac ↔ Windows laptop (≥ 1 hour, both roles) on the new build; if it recurs — send `crash.log` from both machines. The task is considered closed after this check.
- [ ] commit `T5.2: white-screen diagnostics and fixes`

## Pitfalls
- Do not mask the cause with an auto-restart: the safety net (step 5) is needed, but the report must name the root cause or honestly say that it was not found and what exactly was measured.
- `crash.log` and soak must not collect personal data (names, paths outside userData).
- The Windows build comes from the T4.6 path (cross-build); on the Mac reproduce with the same tier as the laptop (`--tier=2x`).
- Check network-code changes against `docs/03` and the T3.x tests; change `PROTO_VERSION`/buildHash only deliberately.

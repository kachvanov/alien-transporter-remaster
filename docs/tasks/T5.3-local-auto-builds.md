# T5.3 — Automatic local dmg and exe builds after changes

**Milestone:** M5 · **Depends on:** T4.5, T4.6 · **Size:** S–M

## Goal
The user is tired of asking for rebuilds after every change. After any merge into `main` that changes game code, an up-to-date pair of builds (macOS dmg arm64 and Windows Setup + portable x64) is built on this Mac by itself into `dist/`, with no human involvement and no cloud CI.

**Why not GitHub Actions:** the build needs the original's assets (`assets/`, ~235 MB, extracted from the SWF). The repository is public, the assets are not in it and must not be (the rights of the original's author, `CLAUDE.md`), and built applications with his graphics must not be published (including as Actions artifacts of a public repository). The user's decision (2026-10-05): locally on the Mac. Do not add `.github/workflows/*` with a build.

## Read before starting
- `CLAUDE.md`, `docs/05-verification.md` §10 (builds), `docs/tasks/T4.5-build-mac.md`, `T4.6-build-windows.md`
- `package.json` (the `build:mac`, `build:win` scripts), `electron-builder.yml`, `tools/build/*`

## Steps
1. **`npm run dist:all`** — a single run that: checks that `assets/` exists and that `out/` is rebuilt (`electron-vite build` once), builds the macOS dmg (arm64) and the Windows NSIS Setup + portable (x64) with electron-builder; puts the result into `dist/`, with names containing the version and the short commit hash (via `BUILD_ID` and `artifactName` in `electron-builder.yml`); writes `dist/BUILD-INFO.json` (commit, date, version, file sizes, `ok`/`failed`, duration of each stage). A failure of one platform must not erase a successful build of the other. Old builds: keep the 2 latest pairs, delete the rest.
2. **Build from the clean state of a commit**, not from a dirty working copy: either `git worktree`/`git archive` of HEAD into a temporary folder with symlinks to `node_modules`/`assets`/`vendor`/`build`/`reference` (as in the agent worktrees), or refuse with a clear error if the tree is dirty. Justify the choice in the report.
3. **A `post-merge` git hook** (in the versioned folder `.githooks/`, enabled by `npm run hooks:install` = `git config core.hooksPath .githooks`): after a merge into `main` in the main copy (not in `.claude/worktrees/**`) it starts `dist:all` **in the background, detached** (`nohup` style, the hook returns immediately), with the log file `dist/build.log`. Only if among the changed files (from the last successfully built commit to HEAD) there are `src/`, `electron/`, `resources/`, `package.json`, `package-lock.json`, `electron-builder.yml`, `index.html`, `electron.vite.config.ts` — do not build for commits touching only `docs/`, `tests/`, `tools/`, `.claude/`.
4. **Locking and restart:** a lock file (with the PID; a stale lock is removed); if a build is already running and a new merge arrives — another build is started after it finishes (not a parallel one), and several merges in a row are coalesced into one additional build.
5. **A macOS notification** on completion/failure (`osascript display notification`: "Build <hash> is ready: dmg + exe" / "Build failed: see dist/build.log").
6. **`npm run dist:status`** — prints the state: whether a build is running, the last successful commit and time, whether `main` is behind the last build, the file paths.
7. Tests: pure logic (the path filter "is a build needed", the lock and the queue, file names, rotation of old builds, `BUILD-INFO`) — unit tests without running electron-builder; a real run of `npm run dist:all` manually in the report (the command and its output, file sizes).
8. In `README.md` (the developer section, if there is one; otherwise in `docs/05` §10) — 5 lines: how to enable the hook and where the builds are. The root README is user-facing — do not bloat it.

## Outputs
`tools/build/dist-all.ts` (+ helper modules), `.githooks/post-merge`, scripts in `package.json` (`dist:all`, `dist:status`, `hooks:install`), `electron-builder.yml` (names with the hash), `docs/05` §10, tests.

## Acceptance criteria
- [ ] `npm run dist:all` on the Mac produces in `dist/` a dmg arm64, a Setup and a portable x64 with the hash in the name and `BUILD-INFO.json`; built from a clean commit.
- [ ] After `npm run hooks:install` a merge with a change in `src/` starts a background build (verified on a test merge in a temporary branch), a docs-only merge does not; the hook returns in < 1 s.
- [ ] Two quick merges in a row = at most one active and one deferred build; the lock does not stick after a crash.
- [ ] The macOS notification arrives on success and on failure.
- [ ] Nothing is published: no `git push`, `gh release`, uploads; `.github/workflows` is not created; `dist/` is in `.gitignore`.
- [ ] `npm run check` is green; commit `T5.3: local auto builds`.

## Pitfalls
- The hook must not break the merge and must not fail if there is no `assets/` (then just a message in the log/notification).
- The hook also fires in the agents' worktrees: skip paths containing `/.claude/worktrees/`.
- The build is heavy (minutes, tens of gigabytes of temporary files) — do not run it in parallel with another build; do not put the load on `git merge` itself.
- The Windows build is cross-compiled on the Mac (T4.6): if Rosetta/Wine is needed, it is already set up, do not redo it.
- Do not touch `docs/ROADMAP.md`, `docs/STATUS.md`, `.claude/**`: wiring the hook into the orchestrator is done by the orchestrator.

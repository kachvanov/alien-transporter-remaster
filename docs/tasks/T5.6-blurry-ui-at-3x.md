# T5.6 — Blurry UI/HUD elements at the 3x tier

**Milestone:** M5 (backlog) · **Depends on:** T1.7, T2.5, T2.6, T4.4 · **Size:** S–M

## Symptom (per the user, 2026-10-05)
At tier **3x** some interface elements look very soft/blurry, while the game itself (shuttle, barrels, passengers) is crisp. Examples named by the user: menu elements and, during play, the **delivery marker** next to a passenger (the small badge with the ship picture showing where the passenger must be delivered). The expected result: everything on the screen has the same sharpness at 3x, as if it were drawn from the 3x raster (the original is vector, so a crisp image is always possible).

## Goal
Find out why these elements are blurry and make them as sharp as the rest of the scene at 3x (and at 2x if affected), without changing the look, layout or game logic.

## Read before starting
- `CLAUDE.md`, `docs/00-overview.md`, `docs/01-architecture.md`, `docs/02-extraction-pipeline.md` (tiers, atlases, `maxTier`, `scale` in the manifest, fonts/glyphs), `docs/05-verification.md` §6 and §9
- `src/render/*` (AtlasLoader, FramePlayer/PixiRenderer, how a node picks its texture and computes anchor/scale; `setSmooth`/Quality), `src/render/atlasMath.ts`, `electron/diskTiers.ts`
- `tools/extract/*` (what is rasterized at which tier; `whitelist.ts`; the `fontglyphs` step), `assets/manifest.json`

## Hypotheses (check each by measurement, do not guess)
1. **Wrong tier for some clips**: the elements come from a lower-tier raster (1x/2x upscaled to 3x) — `maxTier` limits, per-group atlases that do not have 3x, a fallback when a frame is missing in the 3x atlas. Count, per node type, which tier's texture is really drawn at 3x.
2. **Bitmap text/glyphs** (`fontglyphs`, `AntLabel`, `Label`) rasterized at a fixed size and scaled up.
3. **UI/HUD layer drawn with a different scale, resolution or filter** than the scene (a container with `scale`, a non-integer scale, half-pixel positions, `roundPixels`, a separate render group, smoothing/`Quality` setting applied differently).
4. **Texture sampling**: linear filtering of a texture that is minified/magnified by a non-integer factor, mipmaps on/off, `devicePixelRatio` vs `renderer.resolution`, the window size not matching the logical 800×600 × k.
5. Sub-pixel anchor/rect rounding in the atlas (`rect`, trimmed borders, `+2 px` BitmapData bounds from T4.2) making small sprites look soft.
6. Passenger-delivery marker specifically: how `PassengerView`/ship-icon clips get their frames (maybe a `cacheAsBitmap`-like path or a `BitmapData` snapshot at 1x in the port).

## Steps
1. **Reproduce and capture.** Make screenshots of the same scenes at 1x, 2x and 3x (`npm run shot`/`--tier=3x`; scenes: main menu, select-level, garage, pause, Level01 with a passenger waiting and the delivery marker, level-complete). Zoom into the blurry elements (marker, HUD, buttons, captions) and write which ones are affected. Put the pairs (before) into the report (not into git: the original's graphics).
2. **Diagnose**: for the affected nodes find the texture id, atlas page, tier and the applied scale (a debug dump or `--perf-log`-like switch is fine; temporary code must not remain in the commit unless it is a useful, documented dev flag). Record "hypothesis → checked → result".
3. **Fix the cause** in the right layer: extraction (e.g. raster at the proper tier/size, `maxTier` removed where the atlas budget allows), renderer (scale/filter/resolution/rounding), or the text path. Keep the atlas VRAM/RAM budgets of `docs/05` §9 (3x VRAM ≤ 350 MB target; if a fix costs memory, measure and report). If the fix needs a re-extraction (`npm run extract`, which rewrites the shared `assets/`), say so in the report; the orchestrator will make sure no other task runs at the same time.
4. Check that nothing else changed: golden replays unchanged (no simulation change), the T4.2 visual thresholds at the default tier still pass (`npm run shot` + the visual tests), crispness of the already-sharp scene is not worse.
5. Tests: whatever is pure logic (tier/scale selection, texture choice, rounding) as unit tests; a regression test that, for a chosen set of UI clips, the tier used at 3x is 3x (from the manifest/atlas data) if the cause was a wrong tier.

## Outputs
Changes in `src/render/*` and/or `tools/extract/*` (+ regenerated `assets/` if needed), tests, a short note in `docs/02` or `docs/05` if the rules for tiers/UI change.

## Acceptance criteria
- [ ] The blurry elements named above (menu elements, the delivery marker, HUD, captions) are identified with the cause for each, and the before/after screenshots at 3x are in the report.
- [ ] At 3x those elements are as sharp as the scene (zoomed screenshots show no soft edges); 2x is not worse than before.
- [ ] Golden replays unchanged, `npm run check` green, the visual diff thresholds of T4.2 not worse, memory budgets of `docs/05` §9 respected (numbers in the report).
- [ ] Nothing published; the original's graphics are not committed.
- [ ] commit `T5.6: sharp UI at 3x`

## Pitfalls
- The original is vector Flash; sharpness must not come from changing the look (outlines, colours): only the resolution/filtering of the same picture.
- Do not "fix" the visual by blurring/sharpening filters.
- `assets/`, `build/`, `reference/` are shared symlinks: a re-extraction affects all worktrees.
- The user plays with the 3x tier on the Mac (Retina); on the Windows laptop 2x is chosen: check both.
